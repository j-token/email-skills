# 대량 메일 조회 UX 개선 설계

## TL;DR

대량 메일 조회의 UX 문제는 “많은 메일을 본문까지 내려받은 뒤 필터링”하는 구조에서 발생한다.

기본 검색은 `헤더 우선 스캔 → 후보 선별 → 후보 본문 다운로드 → 점진 출력` 구조로 바꾼다.

정확도가 필요한 경우에만 사용자가 승인한 범위에서 본문 전체 검색과 넓은 기간 검색으로 확장한다.

## 문제

메일함 검색은 네트워크 지연, provider 응답 속도, 본문 다운로드 비용, HTML 파싱 비용이 함께 누적된다. 사용자는 검색이 진행 중인지, 몇 건을 확인했는지, 결과가 없는 것인지 아직 찾는 중인지 알기 어렵다.

현재 방식의 UX 위험:

- 검색 완료 전까지 사용자가 기다려야 한다.
- POP3에서 `RETR`를 많이 호출하면 본문 다운로드 비용이 커진다.
- IMAP에서 서버 검색 조건을 적게 쓰면 불필요한 `FETCH`가 많아진다.
- AI가 장시간 침묵하면 사용자는 작업이 멈춘 것으로 느낀다.

## 목표

- 첫 반응은 1초 안에 준다.
- 긴 검색은 진행 상황을 주기적으로 출력한다.
- 본문 다운로드는 후보 메일에만 수행한다.
- 검색 기본값은 빠른 응답을 우선하고, 정밀 검색은 명시적으로 확장한다.

## 비목표

- SMTP 발송 기능은 추가하지 않는다.
- provider별 OAuth 로그인을 일반화하지 않는다.
- 모든 메일 본문을 영구 저장하지 않는다.
- 메일 메타데이터나 검색 결과를 로컬 캐시에 저장하지 않는다.
- 실제 비밀번호나 credential 파일을 로그에 출력하지 않는다.

## 권장 검색 파이프라인

```txt
1. 입력 해석
   날짜 범위, 발신자, 제목 키워드, 본문 키워드, 결과 제한을 분리한다.

2. 빠른 후보 수집
   POP3는 TOP으로 헤더만 조회한다.
   IMAP은 서버 SEARCH 조건을 최대한 사용한다.

3. 후보 축소
   날짜, 발신자, 제목, Message-ID 또는 UIDL 기준으로 본문 조회 대상을 줄인다.

4. 후보 본문 다운로드
   후보에 대해서만 POP3 RETR 또는 IMAP FETCH RFC822를 수행한다.

5. 결과 점진 출력
   검색 중 progress 이벤트와 hit 이벤트를 순차 출력한다.

6. 최종 요약
   스캔 수, 후보 수, hit 수, 누락 가능성, 다음 확장 옵션을 알려준다.
```

## POP3 전략

POP3는 서버 검색 기능이 약하므로 헤더 우선 전략이 중요하다.

권장 흐름:

```txt
LIST로 전체 메시지 수 확인
최신 메시지부터 TOP <msg_no> 0 호출
Date, From, Subject 기준으로 후보 필터링
후보에만 RETR 호출
본문 키워드, 금액, snippet 추출
```

필수 옵션:

- `--scan-limit N`: 최신 N개까지만 확인한다.
- `--max-seconds N`: 지정 시간이 지나면 현재까지 결과로 종료한다.
- `--headers-only`: 헤더 후보만 출력한다.
- `--sender TEXT`: 발신자 필터를 먼저 적용한다.
- `--subject TEXT`: 제목 필터를 먼저 적용한다.

트레이드오프:

- `TOP` 기반 헤더 스캔은 빠르지만 본문 키워드만 있는 메일은 놓칠 수 있다.
- 후보 본문만 `RETR`하면 응답성은 좋아지지만 필터 설계가 중요해진다.
- `scan-limit`을 낮추면 빠르지만 오래된 메일을 놓칠 수 있다.

## IMAP 전략

IMAP은 서버 `SEARCH`를 먼저 활용한다.

권장 서버 조건:

```txt
SINCE 01-May-2026
BEFORE 01-Jun-2026
FROM series_noreply
SUBJECT "네이버 시리즈"
```

한글 본문 검색은 provider와 인코딩에 따라 결과가 불안정할 수 있다. 따라서 기본값은 서버 조건으로 후보를 줄이고, 본문 키워드는 후보 fetch 이후 로컬에서 확인한다.

필수 옵션:

- `--folder NAME`: 검색 폴더를 제한한다.
- `--sender TEXT`: IMAP `FROM` 조건으로 변환한다.
- `--subject TEXT`: IMAP `SUBJECT` 조건으로 변환한다.
- `--body-query TEXT`: 후보 본문을 받은 뒤 로컬에서 검사한다.
- `--max-fetch N`: 본문 fetch 최대 개수를 제한한다.

## 스트리밍 출력

AI와 CLI가 긴 검색을 다루려면 완료 후 한 번에 출력하는 방식보다 이벤트 스트림이 낫다.

권장 옵션:

```txt
--jsonl
```

출력 예:

```jsonl
{"type":"start","protocol":"pop3","since":"2026-05-01","before":"2026-06-01"}
{"type":"progress","scanned":100,"candidates":12,"hits":3}
{"type":"hit","date":"2026-05-23 11:03:56","from":"네이버 시리즈","subject":"구매 내역","amount":3000}
{"type":"done","scanned":652,"candidates":277,"hits":64,"elapsed_ms":58600}
```

AI 응답 정책:

- 시작 즉시 검색 범위와 전략을 알려준다.
- 5초 이상 걸리면 진행 상황을 요약한다.
- 결과가 발견되면 일부를 먼저 보여준다.
- 종료 시 총합과 누락 가능성을 함께 말한다.

## 저장하지 않는 보안 원칙

대량 조회 UX를 개선하기 위해 로컬 캐시를 만들지 않는다. 메일 제목, 발신자, snippet, 금액 후보도 개인정보가 될 수 있으므로 기본 저장 대상에서 제외한다.

허용되는 임시 데이터:

- 현재 프로세스 메모리에 있는 후보 목록
- 현재 검색 결과를 출력하기 위한 일시적 hit 객체
- 사용자가 요청한 최종 요약

저장 금지:

- 원본 비밀번호
- 앱 비밀번호
- 전체 credential 파일
- 메일 본문
- 메일 제목/발신자/snippet 영구 저장
- 금액 추출 결과의 로컬 DB 저장

반복 검색 성능은 캐시가 아니라 더 좁은 검색 조건, 헤더 우선 스캔, 서버 검색 조건, 스트리밍 출력으로 개선한다.

## 검색 모드

기본 모드는 빠른 검색이다.

| 모드 | 목적 | 동작 |
|---|---|---|
| 빠른 검색 | 응답성 우선 | 날짜/발신자/제목으로 후보를 줄이고 후보 본문만 조회 |
| 확장 검색 | 결과 부족 시 | scan-limit, 폴더, 기간을 넓힘 |
| 정밀 검색 | 정확도 우선 | 더 많은 후보 본문을 fetch하고 본문 키워드 검사 |

AI는 처음부터 정밀 검색을 실행하지 않는다. 빠른 검색 결과가 부족하거나 사용자가 명시적으로 요청할 때만 확장한다.

## PDF 첨부 조회와 다운로드 매뉴얼

사용자가 “PDF가 들어간 메일 목록”, “PDF 첨부를 받을 수 있는지 확인”, “PDF를 모두 다운로드”처럼 요청하면 아래 순서로 처리한다.

### 1. IMAP을 먼저 시도한다

IMAP이 가능하면 서버 날짜 조건과 `BODYSTRUCTURE` 조회를 사용한다. 이 방식은 본문 전체를 받지 않고 첨부 구조만 확인할 수 있어 가장 적합하다.

권장 조건:

```txt
SINCE 01-Jan-2026
BEFORE 01-Jan-2027
BODYSTRUCTURE
BODY.PEEK[HEADER.FIELDS (DATE FROM SUBJECT)]
```

처리 기준:

- `BODYSTRUCTURE`에서 `APPLICATION/PDF` 또는 `FILENAME`/`NAME`이 `.pdf`로 끝나는 항목을 찾는다.
- 날짜, 발신자, 제목, 메일 ID, PDF 파일명만 후보 목록으로 출력한다.
- 이 단계에서는 첨부 파일을 저장하지 않는다.

IMAP 인증이 실패하고 provider가 IMAP/SMTP 설정 확인을 요구하면 POP3 fallback으로 전환한다.

### 2. POP3 fallback은 `TOP`으로 후보를 찾는다

POP3는 서버 첨부 검색이 없으므로 `TOP <msg_no> <line_count>`로 헤더와 MIME 앞부분만 확인한다. 전체 본문 다운로드인 `RETR`는 PDF 후보로 좁혀진 메일에만 사용한다.

권장 흐름:

```txt
LIST로 전체 메시지 수 확인
최신 메일부터 TOP <msg_no> 80 호출
Date가 요청 범위 밖이면 건너뜀
MIME part filename 또는 content-type에서 PDF 후보 확인
후보 목록을 먼저 사용자에게 보고
```

진행 상황은 최소 250건마다 보고한다.

```txt
PROGRESS top_checked=250 pdf_candidates=0
PROGRESS top_checked=500 pdf_candidates=0
```

### 3. 다운로드 가능성은 메모리에서 먼저 검증한다

후보 메일에 대해서만 `RETR`를 호출하고 PDF 첨부 payload를 메모리에서 확인한다.

검증 기준:

- MIME part의 filename이 `.pdf`로 끝나거나 content-type이 `application/pdf`여야 한다.
- `get_payload(decode=True)` 결과가 비어 있지 않아야 한다.
- 바이트가 `%PDF`로 시작해야 한다.

검증 결과 예:

```txt
POP 61724 PDF_OK bytes=228708 filename=현대인의생활법률_0602.pdf
```

이 단계에서는 사용자가 다운로드를 요청하지 않았다면 파일을 저장하지 않는다.

### 4. 사용자가 요청한 경우에만 저장한다

사용자가 “다운로드해줘”, “다 다운해봐”처럼 명시적으로 요청하면 PDF 파일을 사용자 소유 다운로드 경로에 저장한다.

권장 저장 경로:

```txt
C:\Users\WinUser\Documents\Codex\email-protocol\downloads\YYYY-pdfs
```

파일명 규칙:

```txt
POP<메일번호>_<첨부순번>_<원본파일명>.pdf
```

예:

```txt
POP61724_01_현대인의생활법률_0602.pdf
```

파일명 처리 규칙:

- Windows에서 사용할 수 없는 문자는 `_`로 치환한다.
- 같은 이름이 이미 있으면 suffix를 붙여 덮어쓰지 않는다.
- 저장 전 `%PDF` 헤더를 다시 확인한다.
- 실패한 첨부는 저장하지 않고 skipped 목록에 이유를 남긴다.

### 5. 최종 보고 형식

목록 조회 후:

```txt
PDF 첨부 메일: N건
PDF 첨부 파일: M개
IMAP 사용 여부 또는 POP fallback 사유
후보 메일 목록
```

다운로드 후:

```txt
저장 위치
저장된 PDF 수
실패/스킵 수
PDF 헤더 검증 여부
파일명 규칙
```

보안 주의:

- 사용자가 다운로드를 명시하기 전에는 파일을 저장하지 않는다.
- PDF 본문이나 첨부 내용을 로그에 출력하지 않는다.
- 계정 설정 파일과 비밀번호는 출력하지 않는다.
- 다운로드 파일은 Git 저장소 밖의 사용자 소유 경로에 둔다.

## 구현 순서

1. POP3 헤더 스캔 분리

   `search_pop.py`에서 `TOP` 기반 후보 수집 함수를 만들고, 후보에만 `RETR`를 호출한다.

2. IMAP 서버 조건 확장

   `search_imap.py`에 `--sender`, `--subject`, `--body-query`, `--max-fetch`를 추가한다.

3. JSONL 스트리밍

   POP3와 IMAP 검색 스크립트에 `--jsonl`을 추가하고 `start`, `progress`, `hit`, `done`, `error` 이벤트를 출력한다.

4. 제한 옵션 추가

   `--max-seconds`, `--headers-only`, `--max-fetch`를 추가해 긴 검색을 중단 가능하게 만든다.

5. AI 운영 규칙 문서화

   `skills/email-protocol/SKILL.md`에 빠른 검색, 확장 검색, 정밀 검색 선택 기준을 추가한다.

## 완료 기준

- 최신 1,000개 POP3 메일에서 후보 검색 시 본문 `RETR` 호출 수가 후보 수와 같아야 한다.
- IMAP 검색은 날짜 외에도 발신자 또는 제목 조건을 서버 `SEARCH`에 반영해야 한다.
- `--jsonl` 사용 시 5초 이상 검색에서 progress 이벤트가 최소 1회 출력되어야 한다.
- 실제 비밀번호는 어떤 모드에서도 출력되지 않아야 한다.
- 메일 본문, 제목, 발신자, 금액 추출 결과를 로컬 DB나 파일에 저장하지 않아야 한다.

## 리스크

- POP3 `TOP` 지원은 provider마다 차이가 있을 수 있다. 실패하면 기존 `RETR` 기반 fallback이 필요하다.
- IMAP 한글 `SUBJECT` 검색은 서버 인코딩 처리에 따라 누락될 수 있다.
- 너무 많은 progress 출력은 AI 응답을 산만하게 만들 수 있으므로 기본 간격을 둔다.

## 다음 결정

첫 구현은 POP3 헤더 스캔과 JSONL 출력부터 하는 것이 좋다. 이 둘은 현재 UX 병목을 가장 작게 건드리면서 체감 대기 시간을 줄인다.
